# 집캐치

청약·공공임대 공고를 찾는 **일반 소비자**를 위한 서비스다.
조건을 한 번 입력하면 지금 지원할 수 있는 후보를 정리해 주고, 관심공고와 일정을 이어서 관리한다.

CRM은 사업자가 내부에서 쓰는 자산이며 소비자에게 파는 관리도구가 아니다.

```
방문 → 조건 입력 → 후보 확인 → 관심 저장 / 알림 선택 → 가입 → 재방문
```

## 로컬 실행

```bash
npm install
cp .env.example .env.local
npm run dev
```

API 키가 없어도 예시 데이터로 전체 화면이 동작한다.
`PUBLIC_DATA_API_KEY` 를 넣고 `/admin` → 청약홈 동기화를 누르면 **실제 모집공고**가 들어온다.

데이터를 영구 보관하려면 Supabase 를 붙인다 — [`docs/setup/supabase.md`](docs/setup/supabase.md) 10분.

```bash
npm run db:check   # 연결 · 테이블 10개 점검
```

운영 화면(`/admin/*`)을 열려면 `.env.local` 에 접속 코드를 넣는다. **기본 암호는 두지 않는다.**

```
ADMIN_PASSCODE=원하는_접속_코드
```

## 화면

### 소비자 (공개)

| 경로 | 설명 |
|------|------|
| `/` | 홈 — 결과 미리보기와 첫 행동 |
| `/analyze` | 3단계 입력 (지역 → 주거비 → 가구·선호) |
| `/results` | 내 후보 — 조건에 맞는 공고 / 예산 초과 공고 분리 |
| `/notices` · `/notices/[id]` | 공고 둘러보기 · 상세 |
| `/saved` | 관심공고 · 알림 설정 |
| `/guide` | 청약 가이드 |
| `/login` | 이메일 로그인 · 가입 |
| `/insights` | 청약홈 공공데이터 통계 |

### 운영 (인증 필요 · `/admin/*`)

종합현황 · 매칭현황 · 고객관리 · 물건관리 · 지원관리.
페이지는 `app/admin/layout.tsx` 에서, API는 각 라우트에서 **매 요청 서버 검사**한다.
공개 메뉴에서 링크만 숨기는 방식은 쓰지 않는다.

## 디자인 규격

`docs/strategy/2026-09-14-consumer-design-direction.md` 가 기준이다.

- **글꼴** — 제목·브랜드는 Gmarket Sans(`app/fonts.ts`, next/font 로 self-host),
  본문·입력·버튼·상세정보는 Pretendard. 모든 글자를 Gmarket Bold로 만들지 않는다.
- **크기** — 홈 타이틀 60/36, 섹션 40/28, 본문 17/16, 카드 보조 14, 출처 13.
  **핵심 정보를 읽는 영역에 16px 미만을 쓰지 않는다.** 320px 에서는 타이틀만 32px까지 완화하고
  설명·입력을 줄여서 해결하지 않는다.
- **색** — 배경 `#F6F8FC` / 카드 `#FFFFFF` / 제목 `#182230` / 본문 `#344054` / 보조 `#667085` /
  주 행동 `#3157D5`. 색은 의미가 있을 때만 쓴다(충족·확인필요·마감긴급).
- **형태** — 카드 20px, 내부 12px, 버튼 12px. 주 버튼 높이 56px(모바일 52px 이상),
  상호작용 영역 최소 44×44px.
- **문체** — 소비자에게 친절하고 명확하게. 업무용 용어(물건·대상추출·통보)를 공개 화면에 쓰지 않는다.
- **시그니처** — 섹션과 공고 카드에 인덱스 번호(`01`, `001`)와 괘선을 쓴다.

## 후보 판정 — 네 가지를 섞지 않는다

`lib/crm/services/scoring.ts` 는 의미가 다른 넷을 분리해 계산한다.
하나의 점수로 합치면 "예산 초과인데 점수가 높은" 결과가 나온다.

| 구분 | 내용 |
|------|------|
| 자격 | 공식 요건. **자격 엔진 전까지 전부 `UNKNOWN`** — 미확인을 불충족으로 단정하지 않는다 |
| 예산 | 사용자가 정한 상한. **기본 후보의 필수조건.** 초과 건은 초과액과 함께 별도 반환 |
| 선호 적합도 | 지역 50% · 면적 25% · 주택유형 25% |
| 마감 긴급도 | 별도 지표. 적합도를 올리지 않는다 |

근거 문장은 점수 구간이 아니라 **실제 값 차이**로 만든다.
`전용 29㎡ — 희망 최소 28㎡보다 1㎡ 넓음`, `상한 8,000만원보다 4,800만원 초과`.

**당첨 확률은 산출하지 않는다.** `lib/subscription-score.ts` 는 과거 당첨가점과의 비교만 제공하며,
표본이 0이면 임의 평균을 만들지 않고 자료 부족으로 표시한다.

## 일정 — 공식 기한과 준비일을 구분한다

`lib/crm/services/scheduling.ts`

- `OFFICIAL` — 공고 원문에 적힌 기한. **원문에 없으면 만들지 않고 미정으로 둔다.**
- `RECOMMENDED` — 공식 기한에서 역산한 준비 권장일. 그렇게 표시한다.

결과발표일 +7일을 공식 계약일로 만들거나, 접수마감일을 서류마감일로 복사하지 않는다.
계약 단계는 당첨 등 선행 조건이 확정돼야 활성화된다.

## 데이터 정책

공개 API는 개별 호실의 실시간 공실 정보를 제공하지 않는다. 계층을 분리한다.

| 출처 | 내용 | 파일 |
|------|------|------|
| 청약홈 | 분양 모집공고 | `lib/adapters/applyhome.ts` |
| LH 청약플러스 | **임대** 모집공고 (국민임대·행복주택·매입임대·통합공공임대 …) | `lib/adapters/lh.ts` |
| CSV | 직접 올린 공고 | `lib/adapters/csv-opportunities.ts` |
| 예시 | 화면 구성을 보여주는 합성 데이터 (`dataOrigin: 'SYNTHETIC'`) | `lib/crm/seed-properties.ts` |

둘 다 `PUBLIC_DATA_API_KEY` 하나를 쓴다. 한 출처가 실패해도 다른 출처는 저장하고,
실패는 `sources[]` 에 그대로 보고한다. **실패를 예시 데이터로 덮지 않는다.**

LH 목록 API 는 지역을 **지역본부 단위**로만 준다(`서울`, `전남·광주`, `전국`).
공고명에서 시·군·구를 추정하지 않는다 — "남악휴먼시아"에서 `남악휴먼시`를 지역으로 잡는 식으로 조용히 틀린다.
대신 서울 자치구 희망자에게는 `서울` 공고를 **부분 일치(45점)** 로 보여주고
`서울 전역 대상 공고 — 세부 지역은 공고문에서 확인하세요` 를 근거에 남긴다.

상가·토지·주차장 공고는 주거 서비스의 대상이 아니므로 수집 단계에서 제외한다.

모든 예시 레코드는 화면에 `예시 공고` 로, 수집된 실제 공고는 `공식 공고` 로 표시한다.
원문 URL이 없으면 없다고 적고, 상세 화면을 원문인 것처럼 안내하지 않는다.

### 값이 없는 칸을 채우지 않는다

청약홈 분양정보에는 전용면적·보증금·월 임대료가 없다. 이 값들은 `null` 로 남기고
화면에는 `공급금액·면적은 모집공고문에서 확인하세요` 로 적는다. 0 으로 채우면 무료 임대처럼 읽힌다.

판정도 같은 원칙이다.

| 상황 | 처리 |
|------|------|
| 면적 미공개 | 적합도에서 제외하고 **가중치 25를 지역·유형에 재분배**. 0점을 주면 "좁다"고 단정하는 셈이다 |
| 금액 미공개 | 예산 초과로도 이내로도 판정하지 않는다. `budget.unverified` 에 남기고 확인 필요로 적는다 |
| 면적 조건 필터 | 면적을 모르는 공고를 조건 불충족으로 떨어뜨리지 않는다 |

**확인된 후보를 먼저 보여준다.** 값이 없으면 가중치 재분배로 점수가 오히려 높아지는데,
점수만으로 줄을 세우면 *아무것도 확인하지 못한 공고*가 1순위가 된다.
`candidate.confidence` 가 `VERIFIED` 인 후보를 `PARTIAL` 보다 위에 두고, 비교 문장도 같은 기준을 쓴다.

소비자 화면이 읽는 실제 공고는 [`lib/consumer/official.ts`](lib/consumer/official.ts) 한 곳을 거친다.
`is_demo = true` 인 운영 시연 데이터는 소비자 화면으로 내보내지 않는다.

## 알림 — 기본 채널은 이메일

가입할 때 이미 받은 이메일로 보낸다. **사용자가 채널 ID를 따로 찾아 입력하는 단계를 두지 않는다.**
텔레그램은 chat id 를 본인이 알아내 적어야 해서 기본 채널로 쓰지 않고, 원하는 사용자를 위한 보조 채널로만 남긴다.

- 수신 동의는 가입과 **별개**로 명시적으로 받는다. `consent: true` 없이 구독을 만들지 않는다.
- 동의 범위·시각·채널을 저장하고, 관심공고에서 해제할 수 있다.
- `RESEND_API_KEY` 가 없으면 발송하지 않고 `PREVIEW` 로 원문만 보관한다.
  화면에도 "발송됨"이 아니라 초안으로 적고, 발송 건수에 집계하지 않는다.
- 운영 측 `kakaoMemoAdapter` 의 "나에게 보내기"는 운영자 본인 계정 테스트이며
  수신자별 발송이 아니다. `TEST_SENT` 와 `DRAFT` 를 발송 완료로 집계하지 않는다.

## 구조

```
app/(consumer)/        소비자 화면
app/admin/             운영 화면 (인증)
app/api/               me · search · notices · saved · alerts · auth · crm(운영)
components/consumer/   소비자 컴포넌트
components/crm/        운영 컴포넌트
lib/consumer/          세션 · 관심공고 · 알림 (현재 메모리)
lib/crm/services/      scoring · matching · scheduling · analytics
lib/admin/auth.ts      운영 접근 제어
app/consumer.css       소비자 디자인 시스템
app/crm.css            운영 디자인 시스템
```

Business logic 은 `lib/` 에 있고 UI 컴포넌트는 표현만 담당한다.

## CRM 파이프라인

```
조건 저장 → (이벤트 발생) → 매칭 → Opportunity Score → 알림 → 클릭 추적 → Lead Score → 지원/문의
```

| 계층 | 위치 |
|------|------|
| 저장소 | `lib/db/repo.ts` — Supabase 없으면 메모리로 폴백 |
| 스키마 | `supabase/schema.sql` |
| 매칭 | `lib/services/matching.ts` |
| 파이프라인 | `lib/services/pipeline.ts` |
| Lead Score | `lib/services/lead-scoring.ts` — 점수표를 한 곳에만 둔다 |
| 알림 채널 | `lib/notifications/provider.ts` + `email.ts`(기본) · `telegram.ts`(보조) |
| 데이터 수집 | `lib/adapters/applyhome.ts` (API) · `csv-opportunities.ts` (CSV) |
| 실제 공고 → 소비자 화면 | `lib/consumer/official.ts` |
| 상담 챗봇 | `lib/services/chat.ts` + `docs/scenarios/consultation.md` |

**경쟁률이 없으면** 해당 가중치(10)를 나머지 항목에 재분배한다. 임의 경쟁 점수를 만들지 않는다.

**알림 임계치**는 `MATCH_NOTIFY_THRESHOLD` 로만 바꾼다. 코드 곳곳에 숫자를 흩뿌리지 않는다.

**클릭 추적**은 `/t/{notificationId}` 를 거친다. 알림 링크가 상세 페이지를 직접 가리키지 않으며
쿼리스트링에 개인정보를 넣지 않는다.

## 운영 화면에서 할 수 있는 것

`/admin/dashboard` 에서:

- **시연 데이터 생성** — 고객 100명 · 기회 60건 (결정적 시드, 전부 `is_demo`)
- **청약홈 동기화** — 공공데이터 API 키가 있을 때 실제 모집공고를 가져온다
- **데모 신규 공실 발생** — H023 공실 0→1 → 매칭 → 알림까지 연쇄 실행

CSV 업로드는 `POST /api/admin/import` (multipart `file` 또는 JSON `csv`).
결과로 `신규 / 업데이트 / 실패` 건수와 실패 사유를 돌려준다.

## 아직 안 된 것

- **Supabase 미연결** — `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` 가 없으면 메모리에 저장되고
  서버 재시작 시 사라진다. 붙이는 방법은 [`docs/setup/supabase.md`](docs/setup/supabase.md).
- **공고의 금액·면적** — 청약홈·LH 목록 API 둘 다 보증금·월 임대료·전용면적을 주지 않는다.
  공고문(PDF) 안에만 있다. 비워 두고 `공급금액·면적은 모집공고문에서 확인하세요` 로 표시한다.
- **LH 공고의 세부 지역** — 목록 API 가 지역본부 단위까지만 준다. 시·군·구를 추정하지 않는다.
- **청약 경쟁률 연동** — `ApplyhomeInfoCmpetRtSvc` 는 열려 있으나 아직 붙이지 않았다.
  공고·주택형·순위별로 값이 달라서 하나의 `competition_rate` 로 줄이는 기준을 먼저 정해야 한다.
  정하기 전까지 `null` 로 두고 그 가중치(10)를 재분배한다.
- **이메일 발송** — `RESEND_API_KEY` 가 있어야 실제로 나간다.
  없으면 `PREVIEW` 로 원문만 보관하며 발송 건수에 집계하지 않는다.
  도메인 인증 전에는 발신자가 `onboarding@resend.dev` 로 고정된다.
- **자격 판정** — 소득·자산·거주기간을 확인하지 않는다. 모든 자격 상태는 `UNKNOWN`.
- **인증 강화** — 이메일·비밀번호만 받으며 이메일 인증·재설정이 없다.
