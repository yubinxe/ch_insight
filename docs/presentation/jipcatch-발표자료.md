# 집캐치 — 대시보드와 루틴 자동화

> 나에게 맞는 집, 내집마련 기회를 사로잡아 보세요
>
> 서비스 https://cheongak-dashboard-opal.vercel.app · 운영 `/admin`

---

## 1. 한 문장

**청약·공공임대 공고를 "찾아서 확인하는 일"을 사람이 매일 반복하지 않게 만든 CRM이다.**

소비자에게는 조건에 맞는 공고를 골라주고, 사업자에게는 그 반응을 고객 단위로 쌓아
누구에게 먼저 연락할지 알려준다. 두 화면은 같은 데이터를 쓴다.

---

## 2. 왜 이 문제인가 — 업계의 실제 하루

청약·임대 중개 실무자의 아침은 20년째 같은 모양이다.

| 시각 | 하는 일 | 걸리는 시간 |
|------|---------|------------|
| 09:00 | 청약홈 접속 → 신규 공고 확인 | 20~30분 |
| 09:30 | LH 청약플러스 접속 → 임대 공고 확인 | 20~30분 |
| 10:00 | 엑셀/수첩의 고객 조건과 눈으로 대조 | 40~60분 |
| 11:00 | 해당 고객에게 개별 연락 (카톡·전화) | 60분+ |
| 수시 | 마감 임박 공고 재확인, 놓친 건 확인 | 30분 |

**하루 2.5~3시간.** 그리고 이 작업은 세 가지 방식으로 실패한다.

1. **누락** — 공고는 매일 20~50건씩 올라온다. 사람이 전부 못 본다.
2. **지연** — 오늘 본 공고가 오늘 마감이면 이미 늦다.
3. **속성 판단** — "이 고객한테 맞나?"를 기억에 의존한다. 담당자가 바뀌면 사라진다.

셋 다 **고객 이탈로 직결**된다. 임대·청약은 마감이 있는 상품이라,
놓친 공고는 다음 달로 미뤄지는 게 아니라 **그 고객과의 관계가 끊긴다.**

## 3. 대시보드 — 무엇을 보는 화면인가

`/admin/dashboard`

기존 부동산 CRM은 **고객 목록**을 보여준다. 집캐치는 **깔때기**를 보여준다.

```
탐지 → 매칭 → 알림 → 반응 → 전환
```

| 지표 | 읽는 법 | 왜 이 지표인가 |
|------|---------|----------------|
| 관리 기회 | 실데이터 / 예시 분리 표기 | 진짜 공고와 데모를 섞으면 숫자를 믿을 수 없다 |
| 오늘 매칭 | 조건 대조를 통과한 건수 | 사람이 눈으로 하던 일의 처리량 |
| 알림 발송 | **초안은 집계하지 않음** | 보낸 것과 만든 것을 같은 칸에 넣지 않는다 |
| 알림 클릭률 | 발송 0이면 `—` | 분모가 0인데 0%라고 쓰면 거짓말이다 |
| Hot Lead | 행동 점수 임계 초과 고객 | 오늘 연락할 사람 |
| 이벤트 스트림 | 탐지→전환 전 과정의 실시간 로그 | 자동화가 **무엇을 했는지** 사람이 감시한다 |

### 설계 원칙 — 숫자를 만들지 않는다

이 대시보드가 다른 제품과 갈라지는 지점이다.

- **당첨 확률을 산출하지 않는다.** 과거 당첨가점과의 비교만 제공하고, 표본이 0이면
  임의 평균을 만들지 않고 "자료 부족"으로 표시한다.
- **경쟁률이 없으면 그 가중치(10점)를 나머지 항목에 재분배한다.** 0점을 주면
  "정보가 없다"가 "경쟁이 치열하다"로 둔갑한다.
- **공고에 없는 날짜는 만들지 않는다.** 결과발표일 +7일을 계약일로 쓰거나,
  접수마감일을 서류마감일로 복사하지 않는다. 없으면 `미정`이다.
- **확인된 후보를 먼저 보여준다.** 금액·면적을 모르는 공고는 가중치 재분배로
  점수가 오히려 높아진다. 점수만으로 줄 세우면 *아무것도 확인 못 한 공고*가 1순위가 된다.

> 실무자가 CRM을 버리는 이유 1위는 "숫자를 믿을 수 없어서"다.
> 한 번 틀린 숫자를 본 사람은 그 화면 전체를 다시 안 본다.

## 4. 루틴 자동화 — 무엇을 대신 도는가

`/admin/routines`

앞의 "하루 2.5시간"을 세 개의 루틴으로 잘라 고정된 시각에 돌린다.

| 루틴 | 주기 | 대신하는 업무 |
|------|------|--------------|
| **공고 동기화 · 신규 매칭** | 매일 09:00 | 청약홈·LH 접속 → 신규 공고 확인 → 고객 조건 대조 |
| **마감 임박 점검** | 매일 08:00 | 마감 3일 이내 공고 추려 관심 고객에게 알림 |
| **오늘 연락할 고객** | 평일 09:30 | 어제 반응한 고객 훑기 → 연락 우선순위 정하기 |

### 루틴 한 건의 구조

화면은 네 덩어리다. 넷 다 같은 지면에 있어야 한다.

1. **상태** — 활성 여부 / 다음 실행 / 마지막 실행 / 최근 성공률
2. **구성** — 트리거(cron), 데이터원, 알림 설정, 켜고 끄기
3. **지침** — 판단 규칙을 **사람이 읽을 수 있는 문장**으로. 코드를 열지 않고 검수한다
4. **실행 이력** — 언제, 수동/예약, 몇 초, 무슨 결과

### 자동화 3원칙

```
1. 루틴은 판단을 대신하지 않는다.
   확인할 건을 골라 올려줄 뿐이다. 자격 판정·당첨 예측은 여기서도 하지 않는다.

2. 성공만 남기지 않는다.
   실패와 사유를 같은 자리에 적는다. 실패가 안 보이는 자동화는
   안 도는 자동화보다 위험하다.

3. 0건도 결과다.
   "오늘 마감 임박 없음"이 기록돼야 어제와 비교할 수 있다.
```

세 번째가 특히 실무적이다. 대부분의 자동화는 할 일이 없으면 아무것도 남기지 않는다.
그러면 **안 돈 것과 돌았는데 대상이 없던 것을 구분할 수 없다.**

### 실제 실행 결과 (2026-09-17)

```
마감 임박 점검   SUCCESS   마감 임박 14건 · 알림 20건
오늘 연락할 고객  SUCCESS   반응 8명 · 우선 응대 1명
공고 동기화      SUCCESS   신규 169건 · 매칭 48건
```

## 5. [실무반영도] 심사 질문에 대한 답

### Q1. 이 자동화가 쓰이는 업무와 업무 요구사항은 무엇인가?

**업무: 공고 모니터링 → 고객 매칭 → 적시 안내 → 응대 우선순위 결정**

공인중개사사무소·분양대행사·임대관리업체의 **매일 반복되는 확인 업무**다.
요구사항을 실무 언어로 풀면 네 가지다.

| # | 업무 요구사항 | 왜 지금까지 안 됐나 |
|---|--------------|-------------------|
| 1 | **누락 없는 수집** — 청약홈·LH 신규 공고를 하나도 빠뜨리지 않는다 | 두 기관 사이트가 분리돼 있고 UI가 다르다. 사람이 두 번 본다 |
| 2 | **조건 대조의 재현성** — 같은 고객·같은 공고면 누가 봐도 같은 결과 | 엑셀+기억에 의존. 담당자가 바뀌면 판단 기준이 사라진다 |
| 3 | **적시성** — 마감 전에 도달 | 확인 시점이 하루만 밀려도 D-1 공고를 놓친다 |
| 4 | **근거 추적** — "왜 이 고객에게 이 공고를 보냈나" 설명 가능 | 기록이 없다. 민원이 오면 방어할 수 없다 |

특히 4번이 업계의 숨은 리스크다. 임대·청약은 **자격요건 오안내가 곧 분쟁**이다.
그래서 집캐치는 알림 본문에 항상 이 문장을 붙인다.

> 소득·자산·거주기간 등 자격요건은 아직 확인하지 않았습니다 — 모집공고문을 확인해 주세요

자동화가 자격을 판정한다고 말하는 순간 법적 책임이 넘어온다. **넘겨받지 않는다.**

### Q2. 이 대시보드와 루틴으로 해당 업무를 얼마나 개선할 수 있나?

#### 정량 — 담당자 1명, 관리 고객 100명 기준

| 항목 | 기존 (수작업) | 집캐치 | 차이 |
|------|-------------|--------|------|
| 공고 확인 | 40~60분/일 | **0분** (09:00 자동) | −50분 |
| 고객 조건 대조 | 40~60분/일 | **0분** (48건 자동 매칭) | −50분 |
| 마감 재확인 | 30분/일 | **0분** (08:00 자동) | −30분 |
| 응대 우선순위 판단 | 20분/일 (감) | **0분** (점수순 목록) | −20분 |
| **합계** | **약 150분/일** | **약 15분/일** (결과 검토) | **−135분** |

> **월 47시간.** 담당자 1명 기준 월 인건비의 약 25~30%에 해당하는 시간이
> 확인 작업에서 **상담·계약**으로 옮겨간다.

#### 정성 — 시간보다 중요한 세 가지

**1. 누락률이 구조적으로 0에 수렴한다**

사람은 공고 50건 중 40건을 본다. 루틴은 50건을 본다.
`(출처, 공고번호)` 기준 upsert라 같은 공고를 두 번 알리지도 않는다.
**수작업의 누락은 확률이지만, 자동화의 누락은 버그다** — 고칠 수 있다.

**2. 판단 기준이 사람에게서 시스템으로 옮겨간다**

지금까지 "이 고객한테 이 공고가 맞나"는 담당자 머릿속에 있었다.
집캐치는 이것을 **가중치와 문장**으로 꺼내 놓았다.

```
지역 30 · 주거비 20 · 면적 15 · 주택유형 15 · 경쟁률 10 · 긴급도 10
근거: "희망 1순위 지역 동작구", "상한 8,000만원 대비 1,500만원 여유"
```

근거를 점수 구간이 아니라 **실제 값 차이**로 만든다.
"적합도 높음" 대신 "희망 최소 28㎡보다 1㎡ 넓음". 고객에게 그대로 읽어줄 수 있는 문장이다.

담당자가 퇴사해도 기준은 남는다. **이게 CRM이 자산인 이유다.**

**3. 응대 순서가 감에서 행동 데이터로 바뀐다**

| 행동 | 점수 |
|------|------|
| 문의 남김 | +30 |
| 지원 제출 | +25 |
| 지원 시작 | +15 |
| 관심공고 저장 | +10 |
| 알림 클릭 | +5 |
| 재방문 | +5 |

`COLD → WARM → HOT → 지원의사`. 오늘 누구에게 먼저 전화할지가 목록으로 나온다.
**연락의 총량이 아니라 순서가 전환율을 만든다.**

#### 개선되지 않는 것 — 정직하게

| 못 하는 것 | 이유 |
|-----------|------|
| 자격 판정 | 소득·자산·거주기간을 확인하지 않는다. 모든 자격 상태는 `UNKNOWN` |
| 당첨 예측 | 확률을 산출하지 않는다. 과거 가점 비교만 제공 |
| 금액·면적 자동 수집 | 청약홈·LH 목록 API가 주지 않는다. 공고문 PDF 안에만 있다 |
| LH 세부 지역 | 지역본부 단위까지만 제공. 공고명에서 시·군·구를 추정하지 않는다 |

**추정으로 채우면 채운 순간부터 틀린 줄 모르고 쓰게 된다.**
비워 두고 "모집공고문에서 확인하세요"로 적는 편이 실무에서 안전하다.

## 6. 시연 시나리오 (5분)

| # | 화면 | 보여줄 것 | 멘트 |
|---|------|----------|------|
| 1 | `/` | 마감 티커가 흐름 | "지금 마감이 가까운 공고가 실시간으로 지나갑니다" |
| 2 | `/analyze` | 3단계 조건 입력 | "지역·주거비·면적. 소득은 묻지 않습니다" |
| 3 | `/results` | 후보 + 근거 문장 | "'적합도 높음'이 아니라 '상한 대비 1,500만원 여유'입니다" |
| 4 | 관심공고 저장 | 가입 게이트 | "저장이 먼저, 가입은 그 다음입니다" |
| 5 | `/admin/dashboard` | 깔때기 + 이벤트 스트림 | "방금 그 행동이 여기 찍혔습니다" |
| 6 | `/admin/routines` | **지금 실행** 클릭 | "매일 아침 2시간이 15초입니다" |
| 7 | 실행 이력 | 성공/실패/건너뜀 | "실패도 같은 자리에 남습니다" |

**마무리 한 문장**

> 집캐치는 **확인을 자동화하고 판단은 사람에게 남깁니다.**
> 부동산에서 판단을 자동화한다고 말하는 제품은, 그 책임도 같이 가져가야 합니다.

## 7. 기술 구성

| 계층 | 구현 |
|------|------|
| 프런트 | Next.js 16 (App Router) · React 19 · CSS 토큰 (Tailwind 미사용) |
| 저장소 | Supabase Postgres · 13개 테이블 · 전 테이블 RLS 차단 |
| 데이터원 | 청약홈 OpenAPI(분양) · LH 청약플러스(임대) · CSV 업로드 |
| 매칭 | 6축 가중치 + 결측 시 가중치 재분배 |
| 알림 | 이메일(Resend) — 채널 ID를 사용자가 찾아 입력하게 하지 않는다 |
| 스케줄러 | Vercel Cron → `/api/cron/routines` (`CRON_SECRET` 인증) |
| 배포 | Vercel |

### 보안

- service_role 키는 **서버 라우트에서만** 읽는다. `NEXT_PUBLIC_` 을 붙이지 않는다
- 전 테이블 RLS 활성 + 허용 정책 없음 → 브라우저에서 직접 접근 시 전부 차단
- `/api/admin/*` 는 매 요청 서버에서 인증 검사. 메뉴에서 링크만 숨기지 않는다
- 알림 링크는 `/t/{id}` 를 거친다. 쿼리스트링에 개인정보를 넣지 않는다
- 분석 이벤트에는 개인정보 원문 대신 **어떤 항목이 들어왔는지**만 남긴다

### 현재 규모 (2026-09-17)

```

예시 공고     60건  (화면 구성 시연용, is_demo 로 끝까지 분리)
고객        102명
매칭         48건
루틴          3개
```

## 8. 데이터 출처

공공데이터포털 — 청약홈 OpenAPI · LH 청약플러스 · 한국부동산원(통계)

공실 이벤트와 일부 임대 물건은 예시 데이터이며 화면에 `예시 공고` 로 표시한다.
실제 공고는 `공식 공고` 배지와 원문 링크를 함께 제공한다.
