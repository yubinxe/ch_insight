## 슬라이드별 시나리오

### 001. 표지 (0:00–0:20)

> "공고는 전부 공개돼 있습니다."
> (2초)
> "그런데 내가 지금 넣을 수 있는 게 뭔지는, 아무도 안 알려줍니다."

- 자기소개로 시작하지 않는다. 첫 20초는 문제에만 쓴다.

### 002. 문제 — 공고는 공개, 판단은 부재 (0:20–1:10)

세 가지만 말한다.
1. **출처 분산** — 분양은 청약홈, 임대는 LH청약플러스로 이원화돼 있습니다.
2. **선별 기능 부재** — 지역·예산·면적·가구형태 기준으로 걸러주는 수단이 없습니다.
3. **일정 관리 공백** — 접수·서류·발표·계약 일정이 공고문 내부에만 존재합니다.

> "정보 접근성 문제가 아니라 판단 지원의 부재입니다."

### 003. 솔루션 — 조건 입력 1회 → 후보 선별 (1:10–2:00)

- 왼쪽 공고 원문(전용면적·보증금이 `—`), 오른쪽 집캐치 출력.
- **강조할 한 줄**: "판단 근거를 점수 구간이 아니라 실측값 차이로 제시합니다."
  > "'적합도 82점'이 아니라 '전용 29㎡ — 희망 최소 28㎡ 대비 +1㎡'로 씁니다. 사용자가 공고 원문으로 검증할 수 있어야 신뢰가 성립합니다."

### 004. 제품 — 6단계 사용자 여정 (2:00–2:40)

방문 → 조건 입력 → 후보 확인 → 관심·알림 → 가입 → 재방문

> "CRM은 내부 운영 자산입니다. 소비자에게 판매하는 관리도구가 아닙니다."
> — 제품 정체성을 정리하는 문장. 반드시 말한다.

### 005. 판정 원칙 — 4축 분리 판정 구조 (2:40–3:40) ★ 핵심

| 구분 | 내용 |
|---|---|
| 자격 | 공식 요건. 자격 엔진 도입 전 전 건 `UNKNOWN` 처리 — 미확인을 불충족으로 단정하지 않음 |
| 예산 | 사용자 설정 상한. 기본 후보의 **필수 조건**. 초과 건은 초과액 명시 후 별도 반환 |
| 선호 적합도 | 지역 50% · 면적 25% · 주택유형 25%. 희망 조건과의 근접도만 산출 |
| 마감 긴급도 | 독립 지표. 적합도 점수에 가산하지 않음 |

> "단일 점수로 통합하면 예산을 초과한 건이 상위에 노출되는 구조적 오류가 발생합니다. 부동산 서비스가 신뢰를 잃는 가장 흔한 경로입니다."

- 여기서 한 번 멈춘다(1.5초). 심사위원이 가장 오래 보는 장표다.

### 006. 데이터 신뢰성 확보 원칙 (3:40–4:30)

- **당첨 확률 미산출** — 과거 당첨가점 비교만 제공. 표본 부재 시 자료 부족으로 표기.
- **결측값 미보완** — 청약홈 분양정보의 전용면적·보증금·월임대료는 `null` 유지, 화면에는 「미공개」.
- **일정 구분 표기** — 원문 기한은 `OFFICIAL`, 역산 준비일은 `RECOMMENDED`.
- **수집 실패 미은폐** — 수집 실패는 `sources[]` 에 원문 그대로 반영.

> "경쟁 서비스가 '당첨 확률 78%'를 제시할 때, 저희는 그 수치를 산출하지 않기로 결정했습니다. 기술적으로 가능하지만 근거가 없기 때문입니다."

### 007. 데이터 — 분양·임대 통합 수집 (4:30–5:00)

- 청약홈(분양) + LH청약플러스(임대: 국민임대·행복주택·매입임대·통합공공임대) + CSV + 예시
- 실제 공고는 `공식 공고`, 합성은 `예시 공고` 로 화면 표기.
- **기술 근거 1개만**: "LH는 지역을 지역본부 단위로만 제공합니다. 공고명에서 시·군·구를 추정하면 '남악휴먼시아'에서 '남악휴먼시'를 지역으로 잡는 오류가 발생합니다. 추정하지 않고 부분 일치로 처리한 뒤 근거에 명시합니다."

### 008. CRM 운영 자동화 — Claude Routines 12종 (5:00–5:50) ★ 데모 포인트

- 화면 전환: **claude.ai → Routines** 목록을 실제로 보여준다.
- 07:00 자동화 상태 점검 / 07:30 데이터 품질 / 08:00 마감임박 메일 / 08:30 일일 브리핑 /
  09:05 신규공고 메일 / 09:30 오늘 연락할 고객 / 10:00 고의도 감지 / 10:30 신청 점검 /
  18:00 전환 퍼널 / 매시 변경감시·재처리 / 월요일 주간 KPI

> "운영자가 매일 아침 DB를 확인할 필요가 없습니다. Supabase 실데이터를 조회하고, 조건 충족 시 Gmail로 발송하며, 실행 이력이 자동 적재됩니다."

- 실행 이력 화면을 1초만 보여주고 넘긴다. 읽지 않는다.

### 009. 수익 모델 — 3단계 수익화 (5:50–6:30)

| 단계 | 내용 | 핵심 지표 |
|---|---|---|
| STEP 1 | 전 기능 무료 제공 — 조건·관심공고 데이터 확보 | 월간 활성 사용자 |
| STEP 2 | 마감 알림 · 정밀 후보 리포트 · 자격 자가진단 유료화 | 유료 전환율 |
| STEP 3 | 시행사·분양대행사 대상 수요·조건 분포 분석 제공 | 계약 단지 수 |

> "축적된 조건·관심공고 데이터는 경쟁사가 복제할 수 없는 자산입니다."

## Q&A 대비

**Q1. 당첨 확률을 제공하지 않는 이유는 무엇입니까?**
> "수요가 있다는 것과 산출 근거가 있다는 것은 별개입니다. 공개 데이터로는 개별 신청자의 당첨 확률을 산출할 근거가 없습니다. 근거 없는 수치를 한 번 제시하면 서비스의 모든 수치가 의심받습니다. 대신 과거 당첨가점 비교를 제공하고, 표본이 없으면 자료 부족으로 표기합니다."

**Q2. 그럼 경쟁 서비스 대비 뭐가 낫나요?**
> "검증 가능성입니다. 저희 근거 문장은 전부 실제 값 차이입니다. '1㎡ 넓음', '4,800만원 초과'. 사용자가 공고 원문을 열어서 맞는지 확인할 수 있습니다."

**Q3. 데이터는 어디서 오나요? 실시간 공실도 되나요?**
> "청약홈과 LH청약플러스 공공 API입니다. 개별 호실의 실시간 공실은 공개 API가 제공하지 않습니다. 그래서 그 기능이 있는 것처럼 만들지 않았고, 합성 데이터는 화면에 '예시 공고'로 구분 표시합니다."

**Q4. Claude Routines는 데모용 아닌가요?**
> "Supabase 실 프로젝트를 읽고 Gmail로 실제 발송합니다. 현재 시드 고객 이메일이 전부 `example.com` 이라 고객 발송은 수신불가로 SKIP되고, 관리자 브리핑은 실제로 발송됩니다. 실고객 주소가 들어오는 순간 그대로 동작합니다."

**Q5. 수익은 언제부터?**
> "STEP 2 구독이 첫 매출입니다. 다만 그 전에 조건 데이터가 일정량 쌓여야 정밀 리포트가 의미를 갖습니다. 그래서 STEP 1을 무료로 오래 끕니다."
