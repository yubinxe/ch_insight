# 집캐치: 제품 전략 및 실제 사이트 진단

검토일: 2026-09-14 / 목적: 다음 개발 단계의 방향 확정과 Claude 실행 지침

수정: 사용자 설명에 따라 소비자 중심 B2C 퍼널로 방향을 확정했다. 이전에 제안한 담당자 동반 실증·B2B2C 진입 전략은 철회한다. 디자인과 퍼널의 최신 기준은 `2026-09-14-consumer-design-direction.md`다. 아래의 데이터·계산 오류 진단은 유지한다.

## 1. 핵심 판단

현재 프로젝트에는 재사용할 만한 화면과 서비스 로직이 있다. 그러나 제품이 약속하는 ‘조건을 기억하고 지원까지 관리한다’는 경험은 아직 연결되지 않았다. 지금 가장 필요한 것은 기능 확장이 아니라 **한 사람의 조건 → 근거 있는 후보 → 지원 준비 → 변경된 일정 대응 → 다음 모집 재검토**를 정확하게 완주하는 것이다.

개발이 애매해지는 가장 큰 원인은 타깃의 충돌이다. 첫 첨부는 개인 주거 CRM과 개인 구독을 설명하고, 후반부는 운영자가 고객 100명을 관리하는 시연을 제안한다. 두 번째 첨부는 다시 개인 서비스 개편을 권한다. 반면 현재 README 84행은 중개·임대관리 실무자를 대상 독자로 명시하고 소비자 앱 문체를 금지한다. Claude 입장에서는 서로 다른 제품을 동시에 구현하라는 주문이다.

‘더 전문적으로’, ‘수상할 수준으로’, ‘Housing OS처럼’은 완료 기준이 아니다. 사용자, 상황, 입력, 출력, 예외, 검증 기준을 정해야 구현이 안정된다.

**확정 방향은 소비자 중심 B2C 서비스다.** 매력적인 첫 화면으로 관심을 얻고, 가입 전에 내 조건의 청약기회를 보여주며, 관심 저장·알림 신청·회원가입·재방문으로 연결한다. CRM은 이 과정에서 쌓인 선호와 행동을 사업자가 직접 활용하는 내부 자산이다. 담당자용 소프트웨어를 판매하는 사업으로 바꾸지 않는다.

## 2. 무엇을 실제 확인했는가

첫 첨부의 [배포 사이트](https://cheongak-dashboard-git-feat-housin-6e4260-yubin-ki-m-s-projects.vercel.app/)를 브라우저로 열었다. 홈의 시각적 구성, 종합현황, 물건관리 로딩 전후, 조건진단 3단계와 분석 결과를 직접 확인했다. 분석에는 서비스가 제공하는 기본 샘플 조건만 사용했다.

프로젝트의 README, CLAUDE.md, CRM 데이터 저장·추천·점수·일정·지표·알림·API·분석 화면과 기존 당첨예측 코드를 함께 읽었다. 배포본과 로컬 소스의 완전한 버전 일치는 검증하지 않았으므로, 아래에서 화면 관찰과 코드 판단을 구분한다. 실제 메시지 발송, 외부 신청, 데이터 초기화는 수행하지 않았다. 모바일·접근성·전체 경로 회귀검증은 이번 검토 범위에 포함하지 않았다.

### 기존 피드백에서 유지할 것과 바로잡을 것

| 기존 제안 | 이번 판단 |
|---|---|
| 정보보다 다음 행동을 제공한다 | 유지. 다만 결과에서 지원 준비로 넘어가는 실제 버튼과 저장이 필요하다. |
| 운영자 메뉴를 무조건 숨긴다 | 조건부. 개인 서비스에서는 맞지만 현재 업무용 제품에서는 필요한 메뉴다. 대상별 진입점을 정한 뒤 분리한다. |
| 물건 0건이므로 데이터가 없다 | 정정. 이번 방문에서는 로딩 중 0건, 완료 후 합성 50건이다. 로딩 상태를 0건처럼 표시하는 문제가 확인됐다. |
| 점수·자격·경쟁도 분리 | 유지·보강. 마감 긴급도까지 적합도에서 분리한다. |
| 0건 화면을 없앤다 | 정정. 진짜 0건은 정직하게 보여줘야 한다. 조건완화 결과와 수집 오류를 구분한다. |
| 재지원률이 가장 중요한 지표 | 조건부. 자동 생성 건과 합성 이력을 제외해야 한다. 주거문제 해결로 졸업하는 고객도 성공이다. |
| 지원이력이 곧 강력한 해자 | 가설. 데이터 보유만으로는 부족하고 재입력·재검토 시간이 줄어드는지 증명해야 한다. |
| 집핏을 집패스로 바꾼다 | 보류. 첨부의 브랜드 충돌 주장은 이번에 별도로 검증하지 않았다. 집캐치를 작업명으로 유지하고 명칭 검토는 출시 전 별도 과제로 둔다. |
| 아이디어 8.5, 락인 9 | 재사용하지 않는다. 정량 평가 근거가 없는 점수보다 관찰 사실과 통과 조건이 유용하다. |

## 3. 즉시 고쳐야 할 문제: 화면과 근거

### P0-1. 예산 초과를 다른 점수로 상쇄한다

실제 샘플 입력은 관악·동작 / 1인가구 / 보증금 상한 8,000만원 / 월세 상한 40만원 / 최소 28㎡다.

| 결과 화면에서 관찰한 내용 | 문제 |
|---|---|
| 2순위: 보증금 1억 2,800만원, 84점 | 상한보다 4,800만원 높지만 ‘지원 가능 물건’ 목록에 들어간다. |
| 3순위: 보증금 1억 2,400만원, ‘예산 상단에 근접’ | 상한을 55% 초과했는데 설명이 이를 축소한다. |
| 6순위: 전용 41㎡, ‘희망면적보다 다소 좁음’ | 입력 최소 28㎡보다 넓은 집을 좁다고 설명한다. |
| 8순위: 신혼희망타운, ‘비선호 유형’ | 가구 관련 지원요건을 확인하지 않은 상태가 단순 선호 문제처럼 보인다. |

`lib/crm/services/scoring.ts`는 보증금과 월세 점수를 평균한다. 한쪽이 크게 초과해도 다른 쪽 점수가 설명 문구를 바꾼다. 면적 설명도 실제 면적 차이가 아닌 점수 구간에서 문장을 선택하기 때문에 방향이 뒤집힌다.

수정: 사용자가 ‘상한’으로 지정한 금액은 기본 후보에서 엄격하게 적용한다. 초과 후보는 별도 ‘조건 변경 시 검토’ 영역에 두고 `보증금 +4,800만원 필요`처럼 정확한 차액을 표시한다. 예산 완화는 사용자 선택으로만 반영한다. 문장은 점수에서 역추정하지 말고 실제 값의 차이로 만든다.

### P0-2. 자격판정이 없는데 ‘적격’이라고 말한다

추천 함수는 점수 계산과 임계값 필터가 중심이다. 읽은 경로에서 연령·소득·무주택 등의 자격 대조는 확인되지 않았다. 분석 화면은 소득을 받지만 해당 추천 점수에는 사용하지 않는다. 연령도 가구유형에 따라 임의로 설정한다.

수정: ‘지원 가능’은 ‘우선 검토 후보’로, ‘적격 고객’은 ‘선호조건 일치 고객’으로 바꾼다. 자격은 `검토한 요건 충족 / 추가 확인 필요 / 확인된 요건 불충족`의 별도 결과로 관리한다. 완전한 공식 자격 확정처럼 표현하지 않는다. 확인되지 않은 필드는 UNKNOWN으로 남긴다. 수집한 입력이 어디에 쓰이는지 설명하고, 미사용 입력은 초기 탐색에서 제거한다.

### P0-3. 일정 자동화가 실제 마감일을 만들어낸다

`lib/crm/services/scheduling.ts` 16~22행에서 서류 제출은 신청 마감일, 계약 체결은 결과일 +7일로 생성된다. README의 ‘공고에 없는 날짜는 만들지 않는다’와 구현이 다르다. 기준 날짜가 존재한다고 별개의 공식 마감일까지 알 수 있는 것은 아니다.

수정: 접수마감·서류마감·계약기간은 각각 원문에서 확인된 별도 필드여야 한다. 준비 권장일과 공식 마감일을 다른 유형으로 표시한다. 계약 일정은 당첨·계약안내 등 선행 조건이 충족되었을 때 활성화한다. 발표일만 있으면 계약일은 미정이다. 정정공고가 오면 기존 날짜와 변경 날짜를 보여주고 영향받은 일정만 갱신한다.

### P0-4. 공식 데이터와 CRM의 연결이 아직 없다

`lib/adapters/housing-source.ts`의 청약홈 어댑터는 키가 있어도 빈 배열을 반환한다. `lib/crm/store.ts`는 합성 주택 50건을 직접 만든다. 통계 화면의 공공데이터 연결과 개인별 CRM 추천의 데이터 연결은 다른 문제다.

수정: ‘공식 API 기반 맞춤추천 완료’로 설명하지 않는다. 먼저 한 기관·한 공급유형의 실제 공고를 CRM 후보 모델에 연결한다. 실데이터 수집 실패를 합성 데이터로 조용히 대체하지 않는다. 데모 모드와 실제 모드를 명시적으로 분리하고 출처·최종 확인시점·갱신 실패 여부를 보인다.

### P0-5. 당첨확률은 검증된 예측모델이 아니다

`lib/subscription-score.ts`의 `predictWinProbability`는 평균·최저·최고 가점과 수동 계수를 조합하고 결과를 5~94%로 제한한다. 코드에서 예측 성능 검증이나 확률 보정 근거는 확인되지 않았다. 기존 통계 메뉴에는 여전히 ‘AI 당첨 예측’이 있다.

수정: 확률 표시를 내리고 ‘과거 당첨가점 참고 비교’로 전환한다. 표본의 기간·공급유형·지역·주택형과 데이터 부족 여부를 보여준다. 가점 계산 규칙 자체도 공급유형별 공식 기준 대조 전에는 공식 계산기로 주장하지 않는다. 공공임대·민영분양·추첨제를 한 가점 체계로 묶지 않는다.

### P0-6. 고객에게 보냈다는 의미와 실제 발송 대상이 다르다

현재 알림 어댑터는 카카오 ‘나에게 보내기’ 또는 미리보기다. 샘플 고객 이름을 넣었다고 그 고객에게 전달되는 것은 아니다. 메시지 본문을 200자로 자르고, 상세 링크가 없으면 청약홈 메인으로 이동한다.

수정: `미리보기 / 테스트 계정 전송 / 고객 채널 전송`을 구분한다. 수신 대상과 동의를 확인하기 전에는 고객 발송을 활성화하지 않는다. 알림의 핵심은 실제 해당 공고·지원건으로 돌아오는 링크다. 외부 실제 발송은 별도 승인된 테스트에서 검증한다. 카카오도 수신 대상별 API를 구분한다. [카카오 공식 문서](https://developers.kakao.com/docs/ko/kakaotalk-message/android)

### P0-7. 재지원률 39%는 사용자가 검증한 성과가 아니다

종합현황에서 고객 100명, 매칭 0명, 통보 0명, 지원 전환 46명, 재지원 18명·39%가 함께 표시됐다. 과거 합성 이력과 새 이벤트가 다른 모수로 섞여 있다.

`analytics.ts`는 모든 지원 객체를 집계하며, 알림은 실제 발송 성공뿐 아니라 생성 기록도 통보 완료로 센다. `store.ts`는 이벤트 후 상위 고객의 지원 객체를 자동 생성한다. 이 흐름을 고객의 자발적 지원 전환으로 집계하면 제품 성과가 부풀려진다.

수정: 데모 지표는 카드마다 ‘시연 데이터’로 표시한다. 동일 기간·동일 고객집단의 행동 이벤트만 전환 퍼널로 연결한다. 자동 준비건 생성과 실제 신청 완료를 나눈다. 과거 이력은 별도 현황이다.

## 4. 사업 방향: 첫 고객과 지불 이유를 구체화한다

| 모델 | 실제 사용자 | 지불 이유 가설 | 먼저 검증할 위험 |
|---|---|---|---|
| 개인 구독 | 적극적으로 주거기회를 찾는 개인 | 반복 확인과 준비 수고 감소 | 무료 대안 대비 유료 가치, 탐색 종료 후 해지 |
| 주거상담 조직용 | 여러 지원자의 공고·서류·일정을 관리하는 담당자 | 건당 처리시간과 누락 감소 | 예산 주체·조달·실제 업무량 |
| 민간 임대운영 CRM | 모집·계약을 관리하는 운영사 | 문의·입주 전환과 공실기간 개선 | 실제 재고 연계, 공공임대 추천과의 업무 차이 |

위 모델 비교 중 이번 프로젝트의 선택은 **개인 소비자 대상 서비스**다. 운영자는 사업자 본인이며 고객관리 화면은 내부에서만 쓴다. 초기 검증 대상도 실제 청약·임대 기회를 탐색하는 소비자다. 대중적인 진입 화면과 개인화 결과가 우선이다.

‘중개사라면 필요할 것’이라는 일반화는 피한다. 공공임대 신청 지원 업무가 일반 중개업자의 매출로 어떻게 이어지는지는 증명되지 않았다. 임대운영사 공실관리와 개인 공공임대 탐색도 별개의 업무다.

초기 범위는 서울 일부 지역의 청년매입임대처럼 한 공급유형으로 제한한다. 다음 릴리스의 성공 문장은 다음과 같다.

> 처음 방문한 소비자가 화면만 보고 자신의 이득을 이해하고, 가입 전에 후보를 확인한 뒤, 결과를 저장하고 새 공고 알림을 받기 위해 자연스럽게 가입한다.

## 5. 다음 화면은 이렇게 설계한다

### 공개 홈

현재 명조 제목·작은 본문·괘선 중심 화면은 업무용 인상을 준다. 소비자 전면은 Gmarket Sans 제목, 큰 본문, 여유 있는 카드와 명확한 버튼으로 재설계한다. 현재 오른쪽 6단계 설명은 소비자가 자신의 결과를 미리 보는 제품 화면으로 교체한다.

추천 제목: **“맞는 공고를 찾고, 지원 준비까지 이어집니다.”**

설명: “지원자의 희망조건과 모집공고를 대조하고, 확인할 요건과 준비 일정을 한곳에 정리합니다.”

주 CTA는 ‘내 조건으로 공고 찾기’, 보조 CTA는 ‘모집 중인 공고 둘러보기’. 공개 화면에는 담당자용 진입 버튼을 배치하지 않는다. 오른쪽은 후보와 저장·마감 알림을 보여주는 소비자용 결과 미리보기로 구성하고, 예시는 명시한다.

### 개인의 진입과 결과

탐색 입력은 희망지역·주거비·면적으로 시작한다. 자격을 확인할 때만 그 공고에 필요한 추가 항목을 요청한다. 단계 수보다 입력의 명확성이 중요하다. 금액은 슬라이더 외에 직접 숫자 입력도 제공하고 단위를 고정한다.

결과 카드는 다음 순서로 읽혀야 한다.

1. 공고명·공급유형·공식/합성 표시.
2. 자격 검토 상태와 미확인 항목.
3. 예산 차액·면적·지역 등 실제 비교값.
4. 선호 적합도와 산출 근거.
5. 공고상 마감시각 또는 ‘미정’.
6. ‘원문 확인’과 ‘지원 준비에 추가’.

점수 숫자가 가장 큰 요소가 되지 않게 한다. 다음 행동을 가장 명확하게 만든다. 현재 결과 하단의 ‘운영 화면 시연’으로는 입력했던 개인의 경험이 이어지지 않는다.

### 내 지원 준비

상단에 ‘오늘 확인할 항목’을 둔다. 각 항목에는 공고명·기한의 출처·진행상태·다음 버튼을 붙인다. 관심 저장과 지원 준비 시작, 실제 접수 완료를 구분한다. 접수 완료는 본인이 확인하거나 공식 확인 자료가 있는 경우에만 기록한다.

### 담당자 업무함

‘고객 100명’보다 `정정공고 검토 대기 / 자격정보 미확인 / 마감 임박 준비건 / 전송 실패`를 우선 배치한다. 고객별로 다음 조치가 보여야 한다. 시장통계는 보조 메뉴로 둔다.

운영자는 담당 지원자만, 개인은 자신의 기록만 본다. 단순히 /admin으로 주소를 옮기는 것은 접근권한 분리가 아니다. 현재 합성 시연을 공개할 수 있어도 실제 고객 자료를 동일한 공개 snapshot에 넣어서는 안 된다.

### 상태별 화면

| 상태 | 화면과 행동 |
|---|---|
| 로딩 | 건수 대신 ‘불러오는 중’. 현재처럼 0건을 먼저 확정하지 않는다. |
| 정확히 일치하는 후보 없음 | 현재 조건을 보존하고 조건 변경안을 사용자가 선택하게 한다. |
| 데이터 수집 실패 | 실패와 마지막 성공시점을 표시하고 재시도한다. ‘공고 없음’으로 바꾸지 않는다. |
| 자격정보 부족 | 부족한 요건과 확인 이유를 보여준다. 조건 충족으로 간주하지 않는다. |
| 마감·취소·정정 | 신청 유도 중단 또는 재검토를 안내한다. 이전 내용을 덮어쓰지 않는다. |

## 6. 추천 방법론: 점수 하나로 합치지 않는다

평가 순서는 `공고 유효성 → 자격 검토 → 예산 등 필수조건 → 선호 정렬 → 준비 일정`이다.

자격은 확률이나 선호점수가 아니다. 필수정보 누락은 UNKNOWN, 확인된 불충족은 별도 사유로 남긴다. 미확인 후보는 참고 영역에서 보여줄 수 있지만 확정 추천처럼 표시하지 않는다. 사용자가 과거 입력한 정보도 공고 기준일에 맞는지 재확인한다.

예산 상한과 선호도를 나눈다. 지역·면적을 엄격 조건으로 둘지도 명시한다. MVP 적합도는 지역 40·주거비 40·면적 20을 초기 가설로 둘 수 있지만 검증된 최적 가중치는 아니다. 공급유형은 범위 제한·자격 검토에서 다룬다. 수집하지 않은 통근시간을 점수에 넣지 않는다.

경쟁도는 같은 모집유형·지역·주택형·기간으로 비교 가능한 경우에만 별도로 제공한다. 데이터가 없으면 ‘자료 부족’이다. 마감은 긴급도 목록으로 정렬할 수 있으나, 가까워졌다는 이유로 집의 적합도가 올라가지는 않는다.

추천 사유는 실제 차이를 설명한다. 예: ‘보증금 상한보다 1,500만원 낮음 / 최소면적보다 1㎡ 넓음 / 두 번째 희망지역 / 소득·자산요건 확인 필요’. 이 정도의 결정적 설명이 근거 없는 긴 AI 문장보다 낫다.

## 7. AI가 맡아야 할 좁고 가치 있는 일

현재 읽은 CRM 흐름에서는 실제 LLM 호출이 확인되지 않았다. 점수와 문장을 코드로 만드는 것은 설명 가능한 자동화지만, 공고문 AI 판독을 구현한 것과 다르다.

다음 한 기능에 AI를 집중한다: **공고문에서 일정·필수요건·서류를 추출하고 원문 위치를 붙이는 검토 초안 생성.**

공식 원문 → 텍스트 추출 → 구조화 초안 → 형식·날짜 검증 → 담당자 검토 → 게시 → 개인별 조건 대조의 순서다. 원문 없는 값은 생성하지 않는다. 모델 자기평가 신뢰점수만으로 자동 승인하지 않는다. 문서 안의 명령은 데이터로 취급하며 실행하지 않는다.

한 번 승인한 공고 추출 결과는 여러 지원자에게 재사용한다. 매칭은 규칙으로, 기한은 확인된 일정으로, 전송은 작업 큐로 처리한다. MCP는 연결 방법일 뿐 고객 가치나 상시 실행 장치가 아니다.

## 8. 데이터·운영 설계

| 단위 | 필요한 정보 |
|---|---|
| 공고 | 기관, 원본 ID, 공급유형, 원문 URL, 수집시각, 상태 |
| 공고 버전 | 변경 해시, 이전 버전, 변경항목, 검토자·검토시각 |
| 공급 주택형 | 공고와 연결, 면적, 임대조건, 모집구분; 개별 호실 공실과 구분 |
| 프로필 버전 | 사용자 입력, UNKNOWN, 입력·확인시점; 임의 연령·소득 금지 |
| 자격 검토 | 공고·프로필 버전, 항목별 충족/미확인/불충족, 근거 |
| 추천 | 적용 필수조건, 점수 버전, 실제 값 비교, 배제·완화 사유 |
| 지원 준비건 | 사용자·공고·회차, 현재 상태, 생성 주체, 실제 신청 확인 여부 |
| 일정 | 공식 기한/권장 준비일 구분, 근거, 시간대, 미정, 활성화 조건 |
| 알림 | 생성/예약/전송/실패/미리보기, 수신대상, 동의, 중복 방지키 |
| 행동 이력 | 조회·저장·준비 시작·신청 확인·결과 확인; 합성/실제 구분 |

현재 `globalThis` 저장은 시연에는 유용하지만 프로세스를 넘어 보존되는 고객 기록이 아니다. 실사용 전에 영속 저장소와 조직·개인별 접근 제어가 필요하다. 재시작·여러 요청에서 기록이 유지되는지 확인한다. 현재 코드에 보이는 위험이며 이번에 배포 데이터 소실을 재현한 것은 아니다.

외부 공고 수집과 알림 작업은 웹페이지가 열려 있지 않아도 실행되어야 한다. 중복 이벤트에는 `기관+원본ID+버전` 기준을, 알림에는 `수신자+공고버전+알림유형+예정시각` 기준을 둔다. 정정공고가 와도 사용자가 완료한 작업을 새로 미완료로 만들지 않는다. 날짜는 Asia/Seoul 기준으로 관리하고 마감시각 미상은 자의적으로 23:59로 확정하지 않는다.

## 9. 검증과 수익모델

초기에는 실제 소비자의 홈 이해도·분석 시작·결과 확인·저장·알림·가입·재방문을 측정한다. 소비자 5명 내외의 사용성 관찰로 첫 화면의 이해와 동선 막힘을 먼저 확인하고, 이후 10~20명의 모집 회차별 사용을 관찰한다. 숫자는 실험 설계안이며 현재 이용자 수가 아니다.

| 지표 | 정의 |
|---|---|
| 핵심 성과 | 해당 기간 실제 모집기회가 있었던 활성 지원자 중 다음 준비 행동을 완료한 비율 |
| 시간 절감 | 같은 검토 업무의 기존 방식 대비 중앙 처리시간 차이 |
| 검토 품질 | 검토한 공고의 핵심 날짜·금액·요건 오류 수와 수정 이력 |
| 준비 전환 | 후보를 본 실제 사용자 중 직접 준비를 시작한 사용자 비율 |
| 재사용 | 첫 회차 참여 후 다음 기회가 있었던 사용자 중 두 번째 회차에서 직접 행동한 비율 |
| 알림 품질 | 실제 전송 성공, 중복, 불필요 알림, 수신 거부를 각각 집계 |
| 해결 성과 | 계약·입주 등 목적 달성으로 탐색을 끝낸 비율 |

초기 내부 통과 기준은 첫 화면 이해도, 결과까지의 완료 여부, 저장·알림·가입의 연결 성공, 다음 모집의 재방문이다. 구체적인 디자인 검증 기준은 최신 소비자 디자인 문서를 따른다. 핵심 날짜 오류는 별도로 점검한다. 표본이 작으면 비율과 함께 실제 인원·건수를 제시한다.

우선은 소비자 활성화와 재방문을 만든다. 개인 프리미엄이나 상담 연결 등의 수익화는 실제 반복 행동과 수요를 확인한 뒤 실험한다. 기관 구독은 이번 방향에서 제외한다. 사업자는 소비자가 제공한 선호·동의한 알림·행동 이력을 활용해 세그먼트별 서비스를 개선한다. 공급자 광고나 수수료가 추후 붙더라도 사용자 적합도 정렬과 분리한다.

고객을 붙잡는 지표보다 다음 회차에 재입력이 얼마나 줄었는지가 중요하다. 서류는 지난번 제출 이력만으로 재사용 가능하다고 보지 않는다. 발급일·공고별 요구조건·정보 변경을 재확인한다.

## 10. 정확성 보완 범위와 데모

아래 표는 기능상 의존관계다. 실제 실행 우선순위는 최신 소비자 디자인 지침의 ‘홈·결과·상세 개편 → 저장·알림·가입 연결 → 재방문·내부 CRM’을 따른다. 정확성 보완은 관련 화면 개편에 함께 포함한다.

| 순서 | 범위 | 완료 조건 |
|---|---|---|
| 1 | 표현·계산·일정·지표 오류 수정 | 본 보고서의 예산·면적 사례가 재발하지 않고 허위 공식 기한·확률이 사라짐 |
| 2 | 실제 공고 1종과 검토된 구조화 데이터 | 원문에서 추천·일정까지 같은 공고 ID로 추적 가능 |
| 3 | 개인 한 명의 준비 흐름 | 조건 저장 → 후보 → 준비 시작 → 일정 → 재방문이 연결됨 |
| 4 | 영속 저장·권한·작업 처리 | 기록 보존, 사용자 간 격리, 중복 방지와 실패 재시도 검증 |
| 5 | 정정공고와 두 번째 모집 | 일정 변경 이력 보존, 기존 조건 재확인 후 재사용 |
| 6 | 소규모 실증 | 관찰한 시간 절감·오류·재사용과 지불 의향을 보고 |

수상 시연은 ‘버튼을 누르면 알림’보다 ‘중요한 오류를 막고 다음 행동까지 연결’하는 장면이 강하다.

권장 3분 시연: 샘플 지원자의 저장 조건 확인 → 공식 원문과 연결된 후보 → 예산 초과 후보가 분리되는 모습 → 자격정보 미확인 표시 → 지원 준비 선택 → 공식 날짜와 권장 준비일 구분 → 정정공고에 따른 일정 변경 → 두 번째 공고에서 조건을 재사용한다. 정정공고와 사용자 행동이 합성이면 화면과 발표에서 명시한다.

실제 공고 1~3건으로 실행 경로를 증명하고, 다양한 예외는 고정된 합성 사례로 재현한다. 데모의 합성 100명·50건을 시장검증 성과처럼 제시하지 않는다. 공식 심사요강과 트랙3 평가기준은 이번 검색에서 확인하지 못했으므로 수상 가능성을 점수화하거나 취지에 정확히 부합한다고 단정하지 않는다.

## 11. 외부 근거와 미확인 사항

- LH는 공고유형·지역·상태·기간 등으로 모집공고를 조회하는 공식 API를 제공한다. 이것을 개별 호실의 실시간 공실 감지라고 해석하지 않는다. [LH 공고 조회 API](https://www.data.go.kr/data/15058530/openapi.do)
- 청약홈 분양정보 API와 기술문서가 공개되어 있다. 로컬 sample의 2026-01-29 문서명과 공식 자료실의 수정일이 대응한다. 실제 연계 범위는 엔드포인트별로 검증해야 한다. [청약홈 API](https://www.data.go.kr/data/15098547/openapi.do), [한국부동산원 기술문서](https://www.reb.or.kr/reb/na/ntt/selectNttInfo.do?bbsId=1268&mi=10251&nttSn=79889)
- 카카오 ‘나에게 발송’은 로그인 사용자 본인에게 전송하는 기능이다. 고객별 대량 알림과 동일하지 않다. [카카오 공식 문서](https://developers.kakao.com/docs/ko/kakaotalk-message/android)
- 상표 등록 가능성, 경쟁사 전체 기능, 유료 수요, 공식 대회 평가기준, 개별 공고의 법적 자격 확정은 검증하지 않았다. 본 문서의 타깃·가중치·실험 기준은 전략 제안이다.

후속 실행은 `2026-09-14-consumer-design-direction.md`를 우선 사용하고, `2026-09-14-claude-implementation-brief.md`를 정확성 보완 기준으로 함께 사용한다.
