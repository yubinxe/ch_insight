# Claude 실행 지시서 — 집캐치 다음 단계

이 문서를 Claude에게 전달하고 단계별로 실행한다. 전체 기능을 한 번에 다시 만들라는 요청으로 사용하지 않는다.

수정된 실행 우선순위: `2026-09-14-consumer-design-direction.md`를 먼저 읽고 소비자 홈·결과·가입 퍼널을 구현한다. 아래 P0는 해당 화면에서 함께 바로잡을 정확성 요건이다. P0만 수정한 뒤 디자인 과제를 완료했다고 보고하지 않는다.

## 공통 프롬프트

당신은 이 프로젝트의 제품 책임자이자 구현 담당자다. 먼저 AGENTS.md, CLAUDE.md, README.md, docs/strategy/2026-09-14-product-review.md와 실제 코드를 읽어라. Next.js 관련 코드를 작성하기 전 node_modules/next/dist/docs/의 해당 가이드를 확인하라.

제품은 실제 소비자를 위한 B2C 청약기회 서비스다. 매력적인 첫인상 → 가입 없는 개인화 탐색 → 결과 확인 → 관심 저장·알림 선택 → 회원가입 → 재방문의 퍼널을 완성한다. CRM은 사업자 본인이 활용하는 내부 자산이며 소비자에게 판매할 관리도구가 아니다. 운영자 동반 실증이나 B2B2C로 방향을 바꾸지 마라. 기존 코드와 사용자의 변경을 보존하고 필요한 범위만 수정하라.

현재 README의 소비자 문체 금지·명조 제목·업무용 메뉴 지침은 사용자의 최신 방향과 충돌하므로 수정하라. 공개 화면은 소비자에게 친절하고 명확한 문체를 사용한다. Gmarket Sans 제목과 Pretendard 본문, 커진 글자, 정교한 간격·상태·모바일 화면은 필수 구현 범위다. 집캐치를 작업명으로 사용하며 새 브랜드를 임의 확정하지 마라. 가상 주택·가상 사용자·합성 경쟁률은 예시로 표시하라. 실데이터 수집 실패를 가상 데이터로 자동 은폐하지 마라.

작업마다 다음을 제출하라: 해결할 사용자 문제, 수정할 파일, 실제 입력·출력 예시, 예외 처리, 검증 결과, 남은 미구현 사항. ‘고도화 완료’라는 설명만으로 끝내지 마라. 별도 승인 없는 실제 고객 메시지 발송·외부 신청·배포는 하지 마라.

## 소비자 디자인 개편에 함께 적용할 P0

소비자 디자인 개편과 함께 아래 오류를 수정한다. 별도의 범용 대시보드, 결제, 지도, 챗봇 확장은 뒤로 미룬다. 코드를 수정하고 적절한 검증까지 수행하라.

### T01. 설명과 입력의 정직성

- `components/crm/AnalyzeView.tsx`, `app/api/crm/analyze/route.ts`, `app/page.tsx`, `README.md` 및 관련 문구를 점검한다.
- 자격 검토가 없는 결과는 ‘우선 검토 후보’, 사람은 ‘선호조건 일치 고객’으로 표시한다.
- 초기 탐색에서 소득을 수집하면서 사용하지 않는 흐름을 없앤다. 정밀 요건 검토는 별도 단계로 설계한다.
- 미입력 연령·소득을 실제 사용자 사실처럼 채우지 않는다. UNKNOWN으로 보존하거나 탐색 입력 모델에서 분리한다.
- ‘상시 감시’, ‘실시간 공실’, ‘실제 발송’ 문구는 구현 상태에 맞춘다.
- 물건 목록 로딩 중에는 0건 대신 로딩 표시를 쓴다. 오류와 빈 결과는 별개다.

완료: 분석을 처음 보는 사람이 자격확정·실데이터·공실연계 여부를 오해하지 않는다.

### T02. 예산 상한과 추천 사유

- `lib/crm/services/scoring.ts`, `matching.ts`를 수정한다.
- 예산 상한은 기본 후보의 필수조건으로 적용한다. 초과 후보는 별도 완화 후보로 반환하고 초과액을 표시한다.
- 면적·금액 사유는 실제 값 차이를 기준으로 생성한다. 점수 구간으로 넓다/좁다를 역추정하지 않는다.
- 날짜 임박은 별도 긴급도이며 선호 적합도를 올리지 않는다.
- 아직 자격 엔진을 구현하지 않았으면 모든 자격 상태는 미확인이다. 미확인을 불충족으로 단정하지 않는다.

완료 사례:

| 입력/상황 | 기대 결과 |
|---|---|
| 보증금 상한 8,000만원, 후보 1억 2,800만원 | 기본 후보 제외; 완화 후보에 +4,800만원 |
| 상한 8,000만원, 후보 1억 2,400만원 | ‘상단 근접’ 금지; +4,400만원 |
| 월세 상한 40만원, 후보 47만원 | 기본 후보 제외; +7만원/월 |
| 최소 28㎡, 후보 41㎡ | 최소보다 13㎡ 넓음; ‘다소 좁음’ 금지 |
| 자격정보 없음 | 추가 확인 필요 |
| 접수 마감·취소 공고 | 현재 신청 권유 금지 |

### T03. 공식 마감과 권장 준비일

- `lib/crm/services/scheduling.ts`, 도메인 모델과 일정 UI를 수정한다.
- 공식 접수·서류·계약 기한을 각각 별도 필드로 둔다. 없는 값은 미정이다.
- 준비일은 RECOMMENDED, 원문 확인 기한은 OFFICIAL로 구분한다.
- 결과일 +7일을 공식 계약일로 생성하지 않는다. 접수마감일을 서류마감일로 복사하지 않는다.
- 계약 단계는 당첨/공식 안내 등 선행 조건에 따라 활성화한다.
- 출처·시간대·미정 여부를 표시한다. 기존 합성 일정도 예시임을 보인다.

완료: 신청 마감만 있는 공고에서 서류마감은 미정, 발표일만 있는 공고에서 계약일은 미정으로 나온다.

### T04. 미검증 당첨확률 제거

- `lib/subscription-score.ts`, `app/insights/page.tsx`, `components/prediction/`와 관련 호출부를 추적한다.
- 임의 계수로 산출한 확률 %와 ‘AI 당첨 예측’ 표시를 제거한다.
- 재사용 가능 부분은 ‘과거 당첨가점 참고 비교’로 전환한다. 출처·기간·표본 단위·자료 부족을 표시한다.
- 확률 필드를 삭제하면 모든 호출부와 타입을 정리한다. 표시만 바꾸고 API에 확률을 남겨 공식 예측처럼 쓰지 않는다.
- 가점 산식의 공식 정확성은 별도 검증 전 확정하지 않는다.

완료: 표본 0건에서 임의 전국 평균·당첨확률을 실제 분석처럼 보여주지 않는다.

### T05. 이벤트·알림·성과의 의미 분리

- `lib/crm/store.ts`, `services/analytics.ts`, `lib/adapters/notification.ts`와 대시보드를 수정한다.
- 이벤트는 후보와 알림 초안을 만들 수 있다. 사용자 의사 없이 생성한 객체는 준비 초안이며 실제 신청 전환이 아니다.
- PREVIEW와 테스트 계정 전송을 고객 발송 완료로 집계하지 않는다.
- 데모 합성 과거이력과 이번 세션 행동을 분리한다. 다른 모수의 숫자를 한 전환 퍼널에 넣지 않는다.
- ‘나에게 보내기’는 테스트임을 표시한다. 실제 수신자별 발송이 구현됐다고 주장하지 않는다.
- 원문 URL이 없을 때 링크를 공고 상세로 가장하지 않는다.

완료: 알림 미리보기만 생성해도 실제 전송 성공과 실제 신청 수는 증가하지 않는다.

### P0 검증 및 보고

중요 계산·일정·집계의 위 사례를 재현 가능한 테스트로 검증한다. 기존 테스트 도구가 없으면 프로젝트 규모에 맞는 최소 검증 방법을 선택하되 수동 확인만으로 복잡한 계산 정확성을 주장하지 마라. lint와 build를 실행하고 환경 문제와 코드 실패를 구분한다. 브라우저에서 샘플 입력 → 결과와 로딩/빈 결과/오류를 확인한다. 바뀐 화면과 남은 미구현을 보고하라.

## 두 번째 실행: 공식 공고 한 건으로 준비 흐름 완주

P0 완료 후에만 진행한다.

1. 실제 접근 가능한 공식 데이터원 한 개와 공급유형 한 개를 선택한다. 서울 청년매입임대를 우선 검토하되 데이터 접근이 안 되면 막힌 이유와 확보 가능한 원문 기반 범위를 명시한다.
2. 원본 ID, 버전, 원문 URL, 수집시각, 검토 상태가 있는 Notice 모델을 만든다. 공고·주택형·개별 공실을 혼용하지 않는다.
3. 공식 공고 1~3건을 연결한다. 누락된 날짜·금액은 생성하지 않는다. 실제 모드에 합성 폴백을 넣지 않는다.
4. 샘플 프로필을 저장하고 사용자별 후보를 보여준다. 상세에서 ‘지원 준비에 추가’를 선택하면 그 사용자와 공고가 연결된 준비건을 생성한다.
5. 준비건에서 원문 확인 → 정보 보완 → 일정 확인 → 신청 완료를 사용자가 각각 기록할 수 있게 한다. 공식 신청을 대신 제출하지 않는다.
6. 재방문 시 같은 프로필과 준비건이 보인다. 운영자와 개인에게 같은 전체 고객 snapshot을 반환하지 않는다.
7. 실제 사용자 도입 전 영속 저장과 접근권한을 구현한다. 사용하는 인프라는 프로젝트의 기존 설정과 사용자 승인을 따른다.

완료: ‘내 조건’의 결과에서 별개의 운영 데모로 빠지지 않고 같은 사용자·같은 공고의 일정까지 연결된다.

## 세 번째 실행: 변경 대응과 AI 근거 추출

1. AI는 원문에서 요건·일정·서류의 초안을 추출한다. 각 값에 원문 위치를 연결하고 검토자가 승인하기 전 자동 확정하지 않는다.
2. 개인 판정은 검토된 공고 규칙과 입력값으로 수행한다. UNKNOWN을 허용한다. 정보 수집 범위는 해당 공고에 필요한 항목으로 제한한다.
3. 신규·정정·취소 공고를 다른 이벤트로 기록한다. 이전 버전과 달라진 내용이 보여야 한다.
4. 정정공고로 공식 기한이 바뀌면 미완료 일정과 예약 알림을 갱신하고 완료 이력은 보존한다.
5. 같은 이벤트의 재처리로 준비건·일정·알림이 중복 생성되지 않게 한다. 프로필 버전도 재분석 키에 포함한다.
6. 탈락 후 새 공고에서 조건을 재사용하되 변경 여부를 재확인한다. 지난 서류의 유효성을 자동 보장하지 않는다.
7. 실험용 사례로만 데모를 진행하고 합성 이벤트를 명시한다. 외부 발송은 별도 승인된 대상과 채널로 검증한다.

완료: 서로 다른 공고를 이어서 지원할 때 입력 수고가 줄고, 잘못되거나 바뀐 날짜를 조용히 유지하지 않는다.

## 최종 수용 기준

- 시연과 실데이터를 화면과 저장 데이터 모두에서 구분한다.
- 자격, 필수 예산, 선호 적합도, 경쟁환경, 마감 긴급도는 다른 의미로 표현한다.
- 자동 생성과 사용자 행동, 실제 발송과 미리보기, 준비건과 실제 신청을 구분한다.
- 원문에 없는 공식 날짜·확률·고객 사실을 만들지 않는다.
- 공식 공고부터 개인 준비 일정까지 추적 가능한 한 경로가 있다.
- 오류·0건·정정·재시도·재방문의 상태가 동작한다.
- 실제 성과 수치는 사용자 검증 전까지 모두 ‘미측정’으로 남긴다.
